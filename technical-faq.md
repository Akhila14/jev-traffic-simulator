# Technical FAQ for the Jev traffic experiment

## How did you get access to Jev?

I used the TypeSafe Jev model through OpenRouter, not through a private TypeSafe deployment. The simulator called OpenRouter's alpha Decisions endpoint with the model ID `typesafe/jev-1.13` and a temporary OpenRouter API key.

The key was supplied through the `OPENROUTER_API_KEY` environment variable. It was not stored in the repository or browser application.

## Did you need a TypeSafe invitation?

Not for this experiment. The calls went through OpenRouter. I did not use or claim access to TypeSafe's direct API for these traffic runs.

## Did you use the `okooo5km/jev` CLI for the simulation?

No. That repository is an unofficial community CLI wrapper that we evaluated separately. The traffic simulator called OpenRouter's Decisions API directly so it could place Jev inside the repeated simulation loop.

## Where did the traffic data come from?

The traffic data was generated by the simulator. It is not Bengaluru Traffic Police, Google Maps, camera, GPS, TomTom or real Sony World Junction data.

Vehicle arrivals were sampled from seeded Poisson processes. The code defines synthetic arrival rates, discharge capacity, rain effects, a temporary blockage and one emergency event. The seeds make the same synthetic traffic reproducible across controllers.

## Why call it Sony World Signal?

Sony World Junction provided a recognizable setting and road names. A public B.PAC/B.MOBILE Inner Ring Road report was used only as location context. None of its traffic measurements were used as simulator inputs.

The accurate description is: **a synthetic two-corridor simulation inspired by Sony World Junction**.

## What exactly did Jev receive?

Every decision state contained:

- simulated time;
- the road currently receiving green;
- how long that green had been active;
- whether a clearance interval was active;
- whether an emergency vehicle was pending;
- queue size for each road;
- the oldest wait on each road;
- arrivals during the previous 30 simulated seconds.

These were synthetic operational values, not an image or video feed.

## What question was Jev asked?

It received one typed `choice` question: choose the next requested signal phase while reducing total waiting and avoiding starvation. It could return only:

```text
serve_inner_ring_road
serve_80_feet_road
extend_current
```

The full instructions and criteria are published in `sony_signal_sim.py`.

## How often did Jev decide?

Every 15 simulated seconds, provided the controller was not already inside a clearance transition. Each 480-second run produced 31 decision records.

“Every few seconds” in the LinkedIn narrative is a simplification; **every 15 simulated seconds** is the precise answer.

## What remained deterministic?

Jev requested a direction. Ordinary code could override that request and enforced:

- minimum green: 15 seconds;
- maximum green: 60 seconds;
- clearance between directions: 4 seconds;
- anti-starvation: switch when the opposing wait reached 75 seconds;
- emergency priority.

For raw-state Jev, the safety layer overrode an average of 5.6 requests per run. This is expected policy enforcement, not a hidden model correction.

## What was the fixed-timer baseline?

It kept the current direction green until it had received 30 seconds of green time, then requested the other direction. It did not inspect queues or waiting times.

## Was there a stronger deterministic baseline?

Yes. The max-pressure baseline calculated:

```text
pressure = queue size + 0.08 × oldest wait in seconds
```

It switched only when the opposing pressure was at least 8% higher. Its overall average wait was 25.09 seconds, close to raw Jev's 24.15 seconds. It is omitted from the short video for clarity but retained in the report and raw results.

## How was the comparison kept fair?

Every controller was run against the same three scenario definitions and the same three deterministic arrival seeds. That produced nine runs per controller. The reported controller values are unweighted means across those nine runs.

## How many runs and Jev calls were made?

There were 36 runs:

- 9 fixed-timer runs;
- 9 max-pressure runs;
- 9 Jev raw-state runs;
- 9 Jev prose-state runs.

The two Jev variants made 279 decisions each, or 558 live Jev decisions in total. The **24.15-second result shown in the video is the raw-state Jev variant**, based on its nine runs and 279 calls.

## What is “Jev with prose”?

It was a separate experimental representation. Instead of exact numbers, the same state was converted into descriptions such as “heavy queue,” “long wait” and “surging arrivals.” It averaged 24.50 seconds of wait. It is not shown in the short video.

## What do the displayed results mean?

Across nine runs per controller:

| Controller | Mean wait | P95 wait | Mean queue |
|---|---:|---:|---:|
| Jev, raw state | 24.15 s | 52.44 s | 28.47 |
| Deterministic max pressure | 25.09 s | 52.22 s | 29.55 |
| Fixed timer | 33.42 s | 71.56 s | 39.47 |

These values describe this simulator only. They do not estimate real waiting times at Sony World Junction.

## Did Jev beat the deterministic rule?

Numerically, raw Jev's mean wait was 0.94 seconds lower. With only three seeds per scenario, that difference is too small to support a general superiority claim.

The defensible conclusion is that Jev substantially beat the fixed timer and performed similarly to the purpose-built deterministic heuristic in this toy model.

## Was confidence useful?

Raw-state Jev returned an average confidence of 0.60; the prose-state variant averaged 0.77. Confidence was useful as an uncertainty signal, but it was not treated as a safety guarantee. Deterministic rules still owned every safety constraint.

## How fast and expensive was it?

Raw-state Jev averaged approximately 0.413 seconds per API call. The complete 558-decision experiment cost `$0.01244606` through OpenRouter. The raw-state variant used in the video accounted for 279 calls and approximately `$0.00657443`.

Pricing and latency can change, so these are measurements from this run rather than guarantees.

## What information was sent externally?

OpenRouter received the synthetic state, the typed question and its three criteria. No real traffic feed, personal information, camera image or private operational data was sent.

## Could this operate a real traffic signal?

No. It has not been tested against the junction's real geometry, lane-level queues, pedestrian phases, legal requirements, hardware faults, public-transport priority, sensor failures or safety-certification process.

The experiment demonstrates a software boundary: a typed model may choose among allowed actions while deterministic code enforces policy and safety.

## Can someone reproduce it?

The simulator, request shape, deterministic baselines, tests and all 36 saved run outputs are published at:

https://github.com/Akhila14/jev-traffic-simulator

The saved results are reproducible as records. A fresh API run may differ if the hosted model or provider changes, even though the model ID is pinned in the code.
